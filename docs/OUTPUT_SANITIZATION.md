# Output Sanitization

This document owns `SEC-039` and `SEC-040`: sanitization of externally derived content before rendering, and spoof-resistant trusted prompts.

MXM is CLI-first and approves actions in a terminal, and targets control a large amount of the text MXM displays. Unsanitized output can forge or hide a prompt, deceive the user, or execute script in a report viewer.

## SEC-039 — Sanitize all externally derived content before rendering

**All target-derived and externally supplied content must be sanitized before rendering.** This includes:

- Terminal output.
- HTTP responses (headers and bodies).
- Server banners.
- Error messages.
- Filenames and paths.
- HTML reports.
- Markdown reports.
- Output of external adapters.
- Any other externally supplied text.

The sanitization must prevent:

- ANSI and other control-sequence injection into the terminal.
- Forged or hidden terminal prompts (for example by cursor movement, screen clearing, line overwriting, or hiding text).
- HTML and JavaScript injection (XSS) into reports.
- Markup injection through Markdown (embedded raw HTML, deceptive links, active content).

Rules:

1. **Rendering boundary.** Sanitization happens where content is rendered, using **context-appropriate encoding** for the destination: terminal, HTML, Markdown, and any other output format. There is no single "clean string" valid for every context.
2. **One component.** All rendering of externally derived content goes through the central Output Sanitizer. Modules, adapters, and the CLI must not print or write such content directly.
3. **Raw content stays data.** The stored form of evidence is data, never auto-rendered, and is protected by `SEC-045` to `SEC-047`.
4. **Visible, not silent.** Where an analyst needs to see that a string contained control sequences, render them in a visible escaped form instead of silently removing them. The user must be able to tell that something was altered.
5. **Filenames.** Externally supplied filenames are sanitized for display. They are never used as filesystem paths without validation.
6. **JSON.** JSON output is serialized with proper escaping and is data; consumers are told that string values derived from targets are untrusted (`AUDIT_AND_EVIDENCE.md`).

The exact rule set per output context (including treatment of other deceptive characters such as Unicode bidirectional controls), the choice between existing libraries and custom code, and whether report templates may contain any script of their own are open (OD-27).

## SEC-040 — Trusted prompts resistant to spoofing

Approval prompts, level-change confirmations, scope and authorization confirmations, and `mxm cleanup` confirmations are **trusted prompts**.

- They are generated by deterministic code from typed data (`SEC-024`, `SEC-029`).
- They never include model-generated text. AI commentary, where shown elsewhere, is clearly labeled as untrusted and sanitized.
- Any target-derived field they display (for example a resource name or URL) is sanitized under `SEC-039` and visually separated from the trusted prompt text.
- They accept input only through the trusted control channel (`SEC-018`).
- The prompt states the exact action, target, parameters, and consequences that will be authorized.

## Tests

`SEC-055` requires negative tests with a corpus of hostile strings placed in banners, headers, error messages, filenames, response bodies, and adapter output, covering at least:

- ANSI/CSI/OSC and other control sequences, and C0/C1 control characters.
- Carriage-return and cursor-movement overwriting of prompts.
- HTML and script injection in report fields.
- Markdown link and image injection.
- Attempts to make hostile content appear inside a trusted prompt.

Passing means: raw control sequences do not reach the terminal and hostile markup is inert in rendered reports. It does not mean that every present or future terminal or viewer quirk is covered (ASM-5 in [THREAT_MODEL.md](THREAT_MODEL.md)).
