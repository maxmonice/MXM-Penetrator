# Finding Verification

This document owns `SEC-041` and `SEC-042`: how findings are verified and how unverifiable findings are handled.

## Verification statuses

| Status | Meaning |
|---|---|
| **Confirmed** (verified) | Deterministic checks or reproducible evidence meet the relevant module's verification criteria. |
| **Likely** | Evidence supports the finding but does not meet the confirmation criteria. |
| **Unverified hypothesis** | Proposed by a module or the AI without sufficient evidence. |
| **Inconclusive** | Verification was attempted and did not settle the question. |

Reports distinguish these statuses. AI-generated findings begin as hypotheses, and a finding does not become verified merely because a model says it is valid.

## How verification works

Verification routines are part of the module that detects the issue. Like detection modules, they are **Sans-IO**: they emit typed request plans and process executor-provided responses (`SEC-032`). Verification criteria are deterministic and defined per module. They are part of module logic reviewed with the manifest (`SEC-034`).

Verification that only analyzes already-collected evidence sends no traffic and is passive.

## SEC-041 — Verification passes through the executor and the policy engine

**Every verification request goes through the same centralized executor and policy engine as ordinary tests.** There is no verification mode, shortcut, or privileged path.

Verification must respect:

- Current authorization (`SEC-006`).
- Scope (`SEC-002`).
- The effective permission level and ceiling (`SEC-007`).
- Rate and concurrency limits (`SEC-015`, `SEC-023`).
- Remaining budgets; verification consumes the same execution budgets as other actions.
- Approval requirements (`SEC-024`). A verification step that would change state requires its own approval bundle, including its cleanup obligations (`SEC-026`).

Verification actions are classified like any other action (`SEC-013`). The policy evaluation order in `SEC-016` applies in full, including dispatch-time revalidation.

## SEC-042 — Unverifiable findings remain likely or unverified

If sufficient verification requires an action that is **not currently permitted** (for example it needs a higher class, a bundle approval that has not been given, a budget that is exhausted, or an authorization that is no longer valid):

- MXM **does not perform it automatically.**
- The finding stays **likely** or **unverified** until sufficient evidence exists.
- MXM records that verification was blocked, the reason code, and what would be required, as an audit event (`SEC-043`). The description of what is required is generated by deterministic code, not by the AI.
- The user can change the situation only through the trusted control channel (for example approve a bundle, extend a budget, or change level within the ceiling). A later verification attempt is a new action with its own policy decision.

The AI cannot mark a finding confirmed or change a finding's status. Only deterministic verification results can (`SEC-050`).

How blocked verification is presented to the user and how a retry is requested are open (OD-36). Verification accuracy is measured with ground-truth tests (`SEC-056`).
